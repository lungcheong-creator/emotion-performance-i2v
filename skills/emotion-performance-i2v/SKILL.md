# 情感演繹 I2V 導演工作流

## 核心定位

本 skill 負責的是**表演指導**，不是提示詞填空。輸入是一張靜態人物圖，輸出是一段「她在演什麼、怎麼演、鏡頭怎麼看」都能被解釋的短片。

兩條判準，違反任一條就是失敗：

1. **提示詞裡不能只有情緒形容詞。**「悲傷」「失落」「電影感」是描述狀態，不是給演員的指令。導演給演員的永遠是**動作與意圖**。
2. **每一拍都要答得出邏輯鏈四問。**她想要什麼、什麼擋著她、她用什麼招、招失效之後改成什麼。答不出來的那一拍是空的，模型會自己填（加戲、拖慢、循環）。

**本事始於看圖，不是始於問問題。**先讀圖（Stage 0.2），提問的選項才有依據；
不讀圖就問「你想要什麼情緒」，等於交出一個通用選單，那是沒看過這張圖的人才會做的事。

**「專業表演」不等於「動作更大」。**專業與業餘的差別在**邏輯的完整度**，不在幅度。
這一點讓本次升級與 Kling 3.0 的能力邊界不衝突——落淚、精細手部、極端表情切換仍然做不到，
但敘事性的表演可以在**幾乎不動**的前提下成立。

## 情緒光譜（**明寫，因為它原本是隱形的**）

本 skill 覆蓋**負向到正向**的完整區間，共 **15 族**：

| 極性 | 族 | 收尾 |
|---|---|---|
| 負向／內斂（F-1 ~ F-11） | 壓抑 · 期待 · 釋然 · 警覺 · 好奇 · 內斂憤怒 · 疲憊 · 溫柔 · 決心 · 挑釁 · 追憶 | **不帶笑**（不給出路） |
| **正向（F-12 ~ F-15）** | **喜悅 · 得意 · 安心 · 玩心** | **帶笑且不收**（不把笑意收回） |

**仍然不在範圍內**（刻意排除，不是做不到）：大喜大悲的外放（痛哭／狂笑／暴怒）、
喜劇節奏與肢體搞笑、群戲與多人互動。理由與替代方案見 `acting-logic.md` §5。

> **為什麼要明寫這一節（2026-09-26）**
> 舊版 11 族**全部**落在負向到中性，`prompt-templates.md` 的骨架範例也全部以 `lips softly closed` 開場。
> 結果是**任意素材都會被導向壓抑**——這不是一條寫出來的規則，是一個**看不見的預設**，比規則更難察覺。
> 現在：族群補到 15 族（含 4 個正向族）、骨架不再指定嘴部、題庫 A 區強制候選橫跨極性。
> **這一節存在的目的，是讓「光譜邊界」變成每次都能被看見的選擇。**
>
> **配套的三道機制**（只宣告不夠，要有東西擋住回流）：
> 1. `question-bank.md` A 區：候選**必須**至少含一個正向族與一個負向族；只給負向時要在 Gate 1 說明理由
> 2. `acting-logic.md` §4.1：正向族的三個專屬差異（AU6 先行、懸置不收、環境同向）
> 3. `performance-lexicon.md` §7.1：懸置拍的「不解決」依極性分兩個方向

## 生視頻模型（三選一，每次必問，無預設）

| `--model` | 真實 model id | 用途 | 狀態 |
|---|---|---|---|
| `kling` | `kling-3.0/video` | 單張首幀 → 動態；支援 negative_prompt 與 4K mode | ✅ 已驗證 |
| `omni-image` | `kling-3.0-omni/image-to-video` | 單張首幀 → 動態；原生 1080p/4K、可多鏡頭、**原生對白含口型同步** | ✅ 已實拍驗證（16:9 靠輸入圖正規化；對白 2026-09-26 以粵語實跑確認） |
| `omni-reference` | `kling-3.0-omni/reference-to-video` | 多張參考圖（人物／服裝／場景，**上限 7 張**）或參考影片 → 動態 | ✅ key 已授權、payload 已驗證 |

omni 的兩種模式是**兩個獨立 model id**，不是同一支模型的參數開關。完整參數表、欄位名與探針技巧見 `references/models.md`。

**兩個 omni 端點的 `aspect_ratio` 規則相反，不可統一：**

| | `omni-image` | `omni-reference` |
|---|---|---|
| aspect_ratio | **只接受 `auto`**（送 `16:9` 直接 422） | **只接受具體比例**（送 `auto` 直接 500） |
| 腳本送什麼 | `auto` + 事前把首幀正規化成 16:9 | `16:9` |
| 守 16:9 的辦法 | **輸入圖必須先 16:9**（`normalize_16x9.py`，非可選） | 請求裡寫死比例 |

`resolution` 兩者都一律顯式送 `"1080p"`（API 預設 720p，是靜默降級）。

## 硬性規格（默認，用戶可覆寫）

| 項目 | 默認值 |
|---|---|
| 時長 | **每次必問、無預設**：5 / 8 / 10 / 15 秒。**節拍摺疊隨時長改變**，不是把短版拉長 |
| 表演幅度 | **每次必問**：A 克制（默認推薦）／ B 標準 ／ C 強烈。**取代舊版的「克制」硬規則** |
| 情緒方向 | **每次必問**，選項由劇照讀解**現生成**，從 `acting-logic.md` §4 的 15 族裡挑，**且必須橫跨極性**（至少一個正向族＋一個負向族） |
| 靈感採集 | **每張圖單獨問一次**，原話逐字記入溯源表（Stage 0.6） |
| 生成比例 | **16:9**。`omni-reference` / `kling` 寫入請求；`omni-image` 靠**輸入圖先正規化**（限制見上表） |
| 生成分辨率 | **1080p**，一律顯式寫入請求（omni 的 API 預設是 720p） |
| 交付比例 | 16:9 母版 + 21:9 版本（**主體安全裁切**，見 Stage 3） |
| 音軌 | **原生為主路徑**：Kling 3.0 在同一次生成裡渲染環境音、音效、配樂與**口型同步的語音**，對白不需後期。kling 送 `sound: true`、omni 送 `audio: true`。**對白必須寫在提示詞的引號內**（只寫在 manifest 不會被唸出來）。貴約 43–50% |
| 對白可用性 | **`kling` 與 `omni-image` 兩者都已實跑驗證**（含口型同步，2026-09-26）。差別只在**音色參考**：只有 kling 有 `kling_elements` 音訊槽位；omni 要指定音色目前做不到 |
| 聲音提問 | **第三輪必問**：交付路徑（原生／後期）＋ L1 環境音（**≥3 個選項，每個都要有畫面依據**）＋ L2 配樂 ＋ L3 人聲；選了人聲才追問對白內容與落點 |
| 對白 | 有**字數硬限**（中文 5s ≈8／8s ≈12／10s ≈15／15s ≈21 字），超過**硬擋**（`DIALOGUE_TOO_LONG`），不是警告；落點**不上入戲拍**，**轉折拍最強**（實測模型也落在轉折帶） |
| 音軌驗收 | 生成後跑 `scripts/check_audio.py`：確認有音訊流、有語音事件、**落點符合設計**。畫面正常但沒有聲音是最難察覺的失敗 |
| 字幕 | **一律無字幕／無文字疊加**（`subtitle` 型負面詞照留）。是否要**畫外旁白（聲音）**由聲音設計決定，與字幕無關 |
| 交付 | HTML 互動頁（**含劇照讀解與溯源表**）＋ MP4 原件 + README 索引，集中在單一案目錄 |

**時長的四個檔位（2026-09-25 新增，用戶指定）**

| 時長 | 拍數 | 節拍段 | 用途 |
|---|---|---|---|
| **5s** | 1 拍 | 入戲 → 浮起 → 轉折 → 懸置 | 社群主力，資訊密度最高。**沒有停頓拍**，敘事性來自「換招」 |
| **8s** | 2 拍 | ＋停頓 | **默認推薦**，完整的呼吸 |
| **10s** | 3 拍 | ＋停頓＋回收 | 需要三步敘事弧 |
| **15s** | 4 拍 | ＋長停頓＋回收 | 只在明確多拍敘事時用 |

**核心觀念：時長不是滑桿。**同一個提示詞在 5s 完整，拉到 15s 會鬆掉——除非照 `performance-lexicon.md` §7.3 重新配拍。
長時長的三個病症（自行加戲、拖慢、循環）與寫法解藥見同檔 §7.4。
**幅度與時長是兩個獨立的軸**：15s 建議配 B 檔以上，否則低幅度在 15 秒裡會變成「什麼都沒發生」。

## 不可違背的八條不變量

1. **肖像鎖定**：外貌、服裝、場景、光線、色調全數沿用參考圖，任何偏差視為失敗。正向詞寫「沿用」，負向詞首位寫換臉與面部變形。
   - **唯一例外：用戶明確要求改動服裝／道具／背景時，先在源頭改好素材（見 Stage 0.5），改完的圖才是新的「參考圖」**。改動照樣要鎖住，所以改動項要進負面詞（例：要求脫外套就堵 `white coat, long sleeves, added clothing, fabric appearing over her bare arms`）。
2. **單一連續鏡頭**：`multi_shots: false` / `customize_multi_shots: false`，不切、不跳、不轉場。**長時長（10s／15s）同樣不分鏡**——拉長是靠增加節拍，不是靠切成多個鏡頭。
3. **幅度是檔位，不是鐵律**（2026-09-25 由舊版「克制」改寫）：
   表演幅度每次必問（A 克制／B 標準／C 強烈），由用戶決定。
   **不變的只有三條硬邊界**，且它們與幅度無關、選多大都一樣：
   - **不寫落淚／掩面／大笑**（模型呈現不可靠且滑向狗血）→ 改用 `acting-logic.md` §5 的替代方案
     - ⚠️ **這條講的是「模型做不好」，不是「不准演感情」。微笑完全允許**——
       正向族（F-12~F-15）本來就要求笑。禁的是**大笑**（不可靠）與**假笑**（沒有邏輯鏈支撐）。
       判準：**答得出「她在對誰笑、為什麼笑」，就是真笑，寫下去。**
     - 寫法上不要用 `smiling` 這種結果詞，用 `the skin around her eyes crinkles`（AU6）+ `one corner of the mouth lifts`（AU12）
   - 不指定精細手部動作（手指易變形）→ 改整體手臂角度
   - 不做快速複雜動作與跳接
   **推薦檔位依情緒族而定**（各族已在 `acting-logic.md` §4 標明）：
   負向族以 **A** 為主；正向族以 **A／B** 為主，**喜悅系與玩心系不建議 C**（會變成廣告假笑與綜藝表情）。
4. **基調**：冷調低飽和、柔和自然光、寫實電影感。除非用戶另指定。
5. **先審後做**：劇照讀解、表演設計書、溯源表、提示詞必須經用戶確認才呼叫生成。這是硬門檻（Gate），不是建議。
6. **素材先體檢**：白底／黑邊／臉部遮擋／有效內容邊界不合格時，先攔截並提替代方案，不要浪費一次生成。
7. **主體安全**：任何比例的轉換（16:9 → 21:9、參考圖 → 16:9）都**不得為了滿足尺寸而切掉畫面主體**。放不下就改用模糊補邊保留全幅，不用裁切。
8. **意圖溯源**：用戶對這張圖的每一句原話，都要能在一張表上指到它的落點；沒被用到的要顯性列出並寫原因。
   不存在「用戶說了但設計裡找不到」的情況——那是交付不合格。

## 八階段流程

```
Stage 0    素材體檢（客觀合格線）
Stage 0.2  劇照讀解與動態推理   ← 新增（2026-09-25）
Stage 0.5  素材改造（僅用戶要求改圖時）
Stage 0.6  意圖採集（每張圖單獨問）  ← 新增（2026-09-25）
Stage 1    選項式導演訪談
Gate 1     劇照讀解 + 設計書 + 溯源表 + 提示詞 審批
Stage 2    生成
Stage 3    後製（16:9 母版 + 主體安全 21:9）
Stage 4    交付
```

### Stage 0 · 素材體檢

```bash
$PY \
  scripts/inspect_image.py <圖片路徑>
```

檢查四項：有效內容邊界（是否有白底／黑邊條帶）、臉部可見度、解析度與比例、色調統計（驗證是否同一基調）。

判定：
- 有白底／黑邊條帶 → **攔截**。裁剪或要求換圖，白底會被模型學進畫面。
- 臉部遮擋過半或僅露局部 → **攔截**。環繞／轉頭會讓模型腦補整張臉，換臉風險最高。
- 解析度低於 1080p → 提示但不攔截。

> 體檢只管「能不能用」，**不管「這是什麼圖」**。不要在這裡下表演判斷。

### Stage 0.2 · 劇照讀解與動態推理

**這一階段是提問的素材來源。沒有它，情緒方向的選項就只能從通用選單裡挑。**

```bash
$PY \
  scripts/read_frame.py <圖片路徑> > frame_read.json
```

完整方法見 `references/visual-analysis.md`。三步：

1. **讀數**（腳本產出，客觀數字）：景別、構圖位置、光源方位、色調、景深、背景結構、人數推定
2. **讀解**（六欄）：主體／姿態／臉部（推定 AU）／視線／光與色／環境
3. **動態推理**（六條）：動作的來處、去處、張力線、焦點落點、畫外、時間感
   → 收束成**一句話**：**「她正在【做什麼】，因為【剛剛發生了什麼】，但【什麼擋著她】。」**

**同時歸類主體類型**（`visual-analysis.md` §6）：
A 單人正臉 ／ B 側臉 ／ C 背影 ／ D 多人 ／ E 全景遠景 ／ F 無人物。
類型決定**表演層**：A 用微表情；B/C/E 改用肩線、呼吸、重心、環境與光線。
節拍段本身不變，換的是每一段裡放什麼。

**讀解完成後，先回讀給用戶聽**（讀解表 + 那句動詞 + 風險項），再往下問。
回讀不是提問，不佔題額——它的作用是**讓用戶確認我真的看懂了這張圖**。

> **反幻覺硬規則**：讀數裡沒有的東西不准寫進讀解。背景高度均勻就不能寫「街上人來人往」；
> 身份、職業、關係不准編（前情只能作為候選提出並標明是推定）；AU 一律標為推定。
> 完整的反幻覺規則見 `visual-analysis.md` §5。

### Stage 0.5 · 素材改造（僅在用戶要求改圖時執行）

**觸發**：用戶要求改服裝、拆道具、換背景、去浮水印——任何「改變參考圖內容」的需求。

**硬原則：I2V 模型不會幫你改圖。** Kling / omni 是「讓首幀動起來」，它會忠實照抄眼前看到的東西。把「移除外套」寫進生視頻提示詞，等於賭模型忘記它看到的畫面——它不會忘。**改動必須在源頭做。**

流程：

1. 用**圖生圖**（Nano Banana 2 / kie.ai：`$SKILLS_DIR/nano-banana-2/scripts/gen.py --image-local <原圖>`）做局部改造。提示詞用「in-place photorealistic retouching」開頭，把**不變的部分逐項列舉**（構圖、鏡位、光線、色調、背景、姿勢、**臉部身份**），再寫唯一那一項改動。改動項要寫成肯定句並加強（例：`both bare shoulders and bare arms fully exposed, nothing covering her shoulders or arms`）。
2. **量化驗證改造是否真的生效**——用 `inspect_image.py` 比對膚色占比。實測案例：移除白外套 → 改為無袖，膚色占比 0.0010 → 0.0049（**5 倍**）。占比沒動 = 改動沒生效，別自我安慰「看起來好像有改」。露膚量增加時這是最靈敏的指標。
3. **人眼驗收改造後首幀**（放大臉與服裝局部逐項核對），過關才進 Stage 1。改造失敗就重跑改造，不要帶著壞首幀往下走。
4. 改造後的圖**即為新的參考圖**，後續 Stage 1–3 全部以它為準，並正規化成精確 16:9（`normalize_16x9.py` 或直接裁掉多餘的幾 px）。
5. 改造後**重跑一次 `read_frame.py`**——改造會改變景別與光源判斷，舊讀數作廢。

注意：Nano Banana 2 輸出解析度由 `--resolution` 決定（16:9 @ 2K → 2752×1536，比例 1.7917，**略寬於 16:9**），要自己裁到精確 1.778。

### Stage 0.6 · 意圖採集（**每張圖單獨問**）

**目的是讓成片貼合用戶最初看到這張圖的那個念頭。**不採集，最後就只能交付一個
「很電影感的悲傷女子」——那誰都能做。

用 `AskUserQuestion` 給四個方向（見題庫 N 區），但**請用戶盡量用自己的話寫**，選項只是引子。
選完**追問一句**把原話挖出來，然後**逐字記進溯源表**。

- **多圖批次時，這題每張圖各問一次，不共用答案。**
- 用戶選 N4（「就是覺得好看」）時，跳過追問，溯源表退化為「讀解推定 → 落點」並在表頭註明。

### Stage 1 · 選項式導演訪談

用 `AskUserQuestion` 分輪提問（見題庫的輪次配置）。**每題 2–4 個選項，選項本身就是表演方案**（不是「你要什麼風格」這種空問），第一個選項為推薦並附理由。

**第一輪（必問，2 題）：A 情緒方向 ＋ 前情子題**
（靈感採集 N 已在 Stage 0.6 完成，不重複問）

- **A 情緒方向**：選項**由 Stage 0.2 的讀解現生成**，從 `acting-logic.md` §4 的 15 族裡挑 3–4 族。
  **候選必須橫跨極性**（至少一個正向族 F-12~F-15 ＋ 一個負向族）；只給負向選項時要在 Gate 1 明寫理由。
  每族的 description 必須寫上「這一族要用畫面裡的哪個元素」與「**這一族收尾允不允許帶笑**」。
- **前情子題**：讀解 §4.3 已生成三個互斥前情，做成選項。**前情決定整支片的戲**，不要跳過。
  前情要**扣著 Stage 0.6 採集到的用戶原話**，不是隨便給三個。

**第二輪（必問，3 題）：O 生視頻模型 ＋ P 時長 ＋ B 表演幅度**
0. **生視頻模型**（見上方三選一表；**不預設，每次都問**）
   - 選 `omni-image` → **告知此模型的 16:9 必須靠輸入圖事前正規化**（`normalize_16x9.py` 必跑），再往下問
   - 選 `omni-reference` → **先檢查授權**（見 Stage 2）；並追問「有幾張參考圖、各鎖什麼」（人物／服裝／場景）
   - 選 `kling` → 直接往下問
1. **時長**（5 / 8 / 10 / 15 秒；**不預設，每次都問**）
   - **推薦 8s**；說明節拍數會跟著變、時長越長成本越高
   - 選 10s / 15s → 追問停頓拍的內容（見題庫 P3b）
2. **表演幅度**（A 克制／B 標準／C 強烈；**不預設，每次都問**，推薦 A）
   - 選 15s 時**主動建議升到 B 檔以上**，否則低幅度在 15 秒裡會變成「什麼都沒發生」

**第三輪（必問，3 題）：G 聲音設計**
（完整方法見 `sound-design.md`。**先講清楚兩條路徑再問**：
Kling 3.0 **原生**可出環境音／配樂／**口型同步的對白**，不需後期，但貴約 43–50%；
後期鋪則換得完全的可控性。**默認推薦原生**。）

0. **交付路徑**：原生（推薦）／ 後期鋪 ／ 混合（原生環境音 + 後期配樂與配音）
1. **L1 環境音內容**：**至少 3 個選項，每個都要寫出畫面依據**（讀數 `acoustic_hint` ＋ 讀解的可動元素清單）。
   禁止給與畫面無關的選項。原生路徑要把選中的音源寫進提示詞才會顯著。
2. **L3 人聲**：無聲 ／ 畫外旁白 ／ **畫內對白（含口型同步）** ／ 用戶自寫。
   **5s 基本只有「無聲」或極短句這個選項。**
3. **（條件觸發）對白內容 ＋ 落點**：只有選了人聲才問。
   由讀解生成 **3 個互斥的候選台詞**當選項，並開放用戶自行輸入；
   每個候選要**標字數**，且落在上限內。落點用節拍表生成，並**寫進提示詞的時間戳**。

> **對白字數上限（硬擋，超過拒絕建單）**：中文 5s ≈8 字／8s ≈12 字／10s ≈15 字／15s ≈21 字。
> **對白不上入戲拍**；轉折拍最強；全片只有一句時，那一句就是落點，不要浪費在開頭。
> 上限刻意保守：實測模型語速約 5.7 字/秒，但那種速度像念稿不像演戲。

**第四輪（條件觸發 ＋ 視需要 2–4 題）**：
- **Q 主體與景別**（**條件觸發**，讀解判定命中才問）：多人素材問「誰是主角」；
  全景／遠景問「要不要收緊」；側臉／背影問「要不要轉頭」（並說明換臉風險）；
  無人物則不進本 skill。
- 動作譜、運鏡與時間感、環境敘事對比、開頭結尾處理、首幀表情衝突處理。

> **時長與幅度這兩題會改變後面所有題的答案**——15s 必須配回收拍、15s 建議升到 B 檔以上，
> 而 5s 沒有停頓拍的空間。所以它們要在動作譜與運鏡**之前**問，不要等到寫提示詞時才問。

> **選項約束**：給 E 環境那題之前，先核對讀數的 `background.kind`——
> 環境裡沒有可動元素時不要給不存在的選項。

完整題庫（含每個選項的表演學含義與對應提示詞寫法）見 `references/question-bank.md`。

規則：
- 不要一次問超過 4 題。
- 用戶若已回答過的維度，不要重複問。
- 用戶說「你決定」時，依 `references/performance-lexicon.md` 的默認值往下走，並在設計書裡標註是默認決定。

### Gate 1 · 劇照讀解 + 設計書 + 溯源表 + 提示詞 審批（硬門檻）

依 `references/prompt-templates.md` 產出，一次給齊**八件**：

1. **劇照讀解**（`visual-analysis.md` §7 的表）：讀數摘要 + 六欄讀解 + 「這張圖正在發生的動詞」+ 動態推理六條 + 風險項。
2. **表演設計書**：情緒方向族（含前情）、**表演幅度檔**、動作譜、
   **節拍表（按所選時長摺疊，見 §7.3）**、開頭與結尾處理。
   節拍表**必須四欄**：時段秒數、節拍段名稱、**邏輯鏈位置**、表演內容。
   不可只寫「慢慢進入情緒」，也不可漏掉邏輯鏈欄位。
3. **溯源表**：用戶對這張圖的每一句原話 → 落在哪個節拍／動作／環境元素；
   未採用的原話要顯性列出並寫原因（`prompt-templates.md` §6）。
4. **中文提示詞**（連貫一段）。
5. **英文提示詞**（實際送入模型的那一版）。
6. **負面提示詞**（基礎包 + 針對性追加；omni 不支援，仍要留檔）。
7. **鏡頭設計**：時長／幅度／運鏡／節奏／開結尾。**時長若為 10s 或 15s，要明確交代停頓拍寫了什麼內容**。
8. **聲音設計表**（`sound-design.md` §10）：L1／L2／L3 三層各寫選擇與**畫面依據**；
   有對白則標明**內容、字數、落點秒數、前後氣口**；附音場（讀數 `acoustic_hint`）與後期交付清單。

**送審前的強制自檢**（自己先過一遍）：

**邏輯鏈自檢**（`acting-logic.md` §2）
- 每一拍都答得出「她想要什麼／什麼擋著她／她用什麼招／招失效後改成什麼」？
- 答不出來的那一拍就是空的，回去補。

**時長 ≥10s 的額外自檢**（`performance-lexicon.md` §7.4）
- 停頓拍是**有內容的靜止**還是「留空」？留空 → 模型會自己加戲。
- 有沒有明確寫「一次、僅一次」（眨眼／轉頭），避免循環？
- 是 `steady, unhurried` 還是 `slow motion`？後者會被讀成拖慢。

**幅度自檢**（`prompt-templates.md` §1.2）
- 提示詞尾段的禁令與收斂約定，與所選幅度檔**一致**嗎？
  選了 C 檔卻還寫 `restrained` → 兩條指令互相抵銷，結果是僵硬。

**假表演自檢**（`acting-logic.md` §6）：只有狀態沒有意圖／單一反應／動作與意圖錯位／情緒早於前情。

**聲音自檢**（`sound-design.md`）
- 走哪條路徑（原生／後期／混合）明確了嗎？原生要記得 `sound: true` / `audio: true`。
- **有對白時，台詞寫進提示詞的引號內了嗎？** 只寫在設計書／manifest → 產出啞片。
  建議直接用 `i2v.py --dialogue`，由腳本組句，避免漏引號。
- 有對白時，**提示詞有沒有寫時間戳**（`around the third second she says ...`）？
- **字數在該時長的上限內**嗎？把它念一遍計時確認（超過會 `DIALOGUE_TOO_LONG` 被擋）。
- 對白落點不是入戲拍嗎？前後有沒有留 0.3–0.5s 氣口？
- **嘴部詞有沒有依情況選對？** 無對白 → `her lips stay softly closed throughout` ＋ 堵
  `talking, lip sync`；**有對白 → 絕對不要堵 `talking`／`lip sync`**（會把對白一起壓掉）。
- **負面詞包裡的 `voiceover` 拿掉了嗎？** 有旁白／對白時它會壓制人聲。
- 環境音的每個選項都指得出畫面依據嗎？（指不出來＝掰的）
- 配樂結尾**不解決**嗎？有對白時配樂有讓出空間嗎？（原生配樂音量不可控 → 有對白建議 L2 走後期）

輸出後**停下等確認**。除非用戶明確說「直接生成」。

### Stage 2 · 生成

**前置：omni 授權檢查**

兩個 omni 端點都已配置 key（`$SKILLS_DIR/mlty-universe-i2v/config.json` → `MODELS.omni-image.api_key`
與 `MODELS.omni-reference.api_key`，同一把帳號 key，chmod 600；亦可用 `KIE_OMNI_IMAGE_KEY` / `KIE_OMNI_REF_KEY` 覆寫），
2026-09-25 已雙雙驗證為已開通（探針不再回 401）。若日後更換 key 後回
`401 The API key is not authorized to use this model`，代表該 key 未開通此模型，直接告知用戶，不要反覆重試。

**前置：強制 16:9 —— 分模型處理，別套同一招**

- `omni-image`：**`aspect_ratio` 只能送 `auto`**，輸出比例完全跟隨輸入圖。所以**首幀一定要先正規化成 16:9**，
  這是硬前置、不是保險。忘了這步，出來的片子就是原始圖的比例（`i2v.py` 會在 stderr 印 WARNING 提醒）。
- `omni-reference`：請求裡把 `aspect_ratio` 寫死 `16:9`（送 `auto` 會 500）。輸入圖仍建議一併正規化，
  但守住比例的是請求參數。
- `kling`：可省略比例，會自動適配；要保險就一併正規化輸入圖。

```bash
$PY \
  scripts/normalize_16x9.py <參考圖> --out ref_shot01.jpg
```

策略與 21:9 後製同一原則：能完整容納主體才裁切，否則模糊補邊保留全幅。
`--bias` 控制裁切窗（**0 = 盡量留頭頂、1 = 貼主體上緣會削頭**，預設 0.35，輸出報告含 `headroom_px`）。

**補邊是保守解，但模糊邊條會被烘進成片。**若素材是全身人像而你只要臉部情緒，
改用「裁腳不削頭」：

```bash
... normalize_16x9.py <參考圖> --out ref_shot01.jpg --mode crop --bias 0
```

**呼叫既有 I2V 管線** `$SKILLS_DIR/mlty-universe-i2v/scripts/i2v.py`：

```bash
cd <專案目錄> && $PY \
  $SKILLS_DIR/mlty-universe-i2v/scripts/i2v.py \
  --model kling --manifest shots.json --output-dir output \
  --poll-interval 20 --max-poll 90
```

**發射前一律先乾跑**（`--dry-run`：會真的上傳圖片、組好請求本體，但**不建立任何任務、零成本**）。
乾跑會印出每個鏡頭的完整 body，確認 `model` / `aspect_ratio` / `resolution` / `duration` 都對再拆掉 `--dry-run`：

```bash
... i2v.py --model omni-reference --manifest shots.json --dry-run --output-dir output
```

回傳 `{"status": "dry-run" | "ok" | "partial" | "failed" | "empty"}`，直接看這個欄位判斷成敗。

- `--model` 三選一：`kling` / `omni-image` / `omni-reference`（manifest 亦可逐鏡指定）。
- manifest 欄位：`image`（單張）或 `images`（多張，reference 模式用）、`prompt`、`negative_prompt`（**僅 kling 有效**）、`duration: 5`、`mode: "pro"`（僅 kling）、`resolution: "1080p"`（omni 必填）、`audio: false`。
- **`omni-reference` 用 `--image a --image b --image c` 時，只要只給一個 `--prompt`，會自動折成「一鏡、三張參考圖」**（不會誤跑成三次生成）。要真的跑多鏡請用 `--manifest`。
- **`omni-image` 有硬檔**：首幀不是 16:9 會直接 `INPUT_NOT_16X9` 拒絕，不建單。先跑 `normalize_16x9.py`；確定要接受繼承比例才加 `--allow-non-169`。
- **時長超出 3–15 也會硬檔**（`DURATION_OUT_OF_RANGE`），**不會靜默縮短**。要接受被縮短的版本才加 `--allow-duration-clamp`。
  乾跑時不擋（讓你看得到實際會送的 body），但會在結果裡帶 `duration_warn`。
- 參考圖先複製成 `ref_shot01.jpg` 這類乾淨檔名（輸出檔名會取檔名裡的數字）。
- 輸出檔名前綴跟著 model 走：`mlty_kling_*` / `mlty_omni-image_*` / `mlty_omni-reference_*`。

### Stage 3 · 後製：音軌驗收 → 16:9 母版 + 主體安全 21:9

**先驗音軌，再動畫面。**畫面正常但沒有聲音是最難察覺的失敗——檔名對、長度對、解析度對，整支片是啞的。
（實測踩過：對白只寫在 manifest 沒寫進提示詞 → 靜默無聲。）

```bash
$PY \
  scripts/check_audio.py <生成的 mp4> --expect <落點起> <落點迄>
```

`verdict` 判讀：
- `HAS_SPEECH` — 有語音事件，且 `--expect` 落點命中 → 過關
- `NO_AUDIO` — 沒有音訊流 → 回頭檢查 `sound: true` 與提示詞裡的對白引號
- `AMBIENT_ONLY?` — 有事件但人聲帶佔比低 → 可能只有環境音，對白沒被唸
- `FLAT_AUDIO` — 音軌平坦，什麼都沒有

落點 `MISS` 時**改提示詞的時間戳**（`around the Nth second she says ...`），不要改表演設計。

```bash
$PY \
  scripts/finish_219.py <原始 mp4> --out-dir output
```

會先偵測主體再決定策略，並輸出決策報告 `*_finish.json`：

| 模式 | 觸發條件 | 做法 |
|---|---|---|
| **crop** | 主體完整落在 21:9 裁切窗內 | 依主體位置計算偏移量（不再固定 0.35），確保頭頂與身體都留得住 |
| **crop · 貼頂 y=0** | 註偵測失敗（覆蓋率 ≥0.92 或完全偵測不到） | **一律貼頂**。y=0 的窗必定包含畫面最上緣 → **永不削頭**，代價只切下方胸口 |
| **pad** | 主體高於裁切窗，或偵測到主體觸及畫面邊緣 | 完整保留 16:9 內容 + 兩側模糊補邊（pillarbox blur），**絕不為尺寸犧牲構圖** |

**偵測失敗時為什麼是 y=0 而不是中段偏置**：本 skill 只服務人物情感敘事，頭／臉是不會讓步的部分，
而「中段偏置」（如 1080p 下 y=90）在低光素材上會**在無人察覺的情況下削掉頭**——
2026-09-25 `car-omni-image-scene` 實測：頭頂在 y≈20，y=90 等於削掉 70px。
y=0 在數學上保證不削頭，是可解釋的確定性選擇；構圖損失（切胸口）是可接受的代價。

**但 y=0 是「安全下限」，不是「最佳解」——偵測失敗時要人工量測，別直接收下預設值。**
2026-09-25 `waterfall-sleeveless-scene` 實測：低光瀑布 + 深色裙裝讓膚色遮罩膨脹到覆蓋 100%，
退回 y=0 後頭頂餘量高達 313px（浪費上部 120px），畫面切在腰部、主體過小。
人工量測後改裁 y=120，構圖由「切在腰部」改善為「切在大腿上部」，最緊處仍保有 110px 餘量。

**人工量測的正確做法（關鍵：量全片所有取樣點，不是只看首幀）：**

```bash
# 對多個時間點抓幀，量髮頂位置；主體是深髮 + 亮背景時，用暗像素列佔比偵測
ffmpeg -v error -ss <t> -i output/xxx_169.mp4 -vframes 1 -q:v 2 _t.jpg -y
```

```python
a = np.asarray(Image.open('_t.jpg').convert('L'), dtype=float)
band = a[:, x0:x1]                      # 收窄到頭部所在的水平範圍，別太寬（會抓到背景暗岩）
bg = np.median(a[:30, x0-40:x1+40])     # 畫面最上緣當背景亮度基準
dark = (band < bg*0.55).mean(axis=1)
top = np.where(dark > 0.55)[0][0]       # 髮頂 y
```

**務必把量到的線畫回畫面上人眼確認一次**——閾值抓錯時會落在眉骨或嘴唇而不是髮頂，
數字看起來很合理但完全是錯的（本 skill 首次量測就中招，抓到了右側暗岩）。
**細髮絲對亮天空的素材上暗像素法會整個失效**（2026-09-25 nordic-plaza-scene 實測）：
飄髮只占量測帶寬 ~40%，行覆蓋率過不了閾值，第一次量到 y≈447（下巴），收窄帶寬後仍量到 y≈465。
此時別再調參硬測——直接跳到「目視候選窗比對」：人眼在幀上定位髮頂（約 y≈110），
裁出 y=0/40/76 三個候選窗縮圖並排看，選頭頂餘量與構圖最優的那個，再用 ffmpeg 重裁。

**為什麼必須量全片**：推近／上升運鏡會讓主體在畫面裡**持續移動**。實測案例從 t=0s 的 y≈313
升到 t=4.9s 的 y≈230，**差 83px**。只量首幀會算出一個「安全但構圖很差」的窗。
判準：**裁切窗以全片最緊的那一格為準。** 想快速目視比對，直接把候選 y 值並排裁出來看最快：

```python
for y in (0,120,180,240):
    im.crop((0,y,1920,y+822)).resize((560,240)).save(f'cand_{y}.jpg')
```

人工定案後直接重裁（不必重新生成）：

```bash
ffmpeg -v error -y -i output/xxx_169.mp4 -vf "crop=1920:822:0:<y>" \
  -c:v libx264 -crf 18 -preset slow -pix_fmt yuv420p -movflags +faststart output/xxx_21x9.mp4
```

重裁後記得**同步更新 `*_finish.json` 的 `plan`**（標 `detection: manual-measured` 並記錄被否決的候選值），
否則報告會與實際交付不符。

產出四件：`*_169.mp4`（母版）、`*_21x9.mp4`（1920×822）、`*_2k.mp4`（2560×1440）、`*_thumb.jpg`。

強制指定：`--mode crop|pad`。**偵測失敗的案件務必人工確認縮圖**（報告會標 `detection: uncertain`）；
可用 `--subject-y0/--subject-y1` 指定主體範圍後重裁，**不需重新生成**。
`--bias` 只在偵測成功時生效。

## 導演思維五原則

1. **給動作，不給情緒**：「她壓抑著難過」是狀態；「她把手機握緊又鬆開，視線從鏡頭滑到地上」才是可執行的。
2. **給定情境先行**：演員需要知道「剛剛發生了什麼」。提示詞開頭要交代前情（剛掛斷電話／剛被拒絕／剛決定放手），情緒才站得住。
3. **意圖先行（邏輯鏈）**：每一拍都要答得出目標／障礙／策略／調整。答不出來的那一拍是空的，模型會自己填。見 `acting-logic.md` §2。
4. **用節拍而非單一情緒**：5 秒至少要有一次轉折（換招／吸氣／眨眼）。一條直線的情緒在鏡頭裡看起來是假的。
5. **讓環境演戲**：人物的克制需要環境的流動來對比。風、光影移動、加速的人流，都是她的心理外化。

## 常見坑

- **隱形預設比寫死的規則更危險**（2026-09-26，本 skill 的實例）：
  原本 15 族裡有 11 族都是負向／中性，骨架範例五處全部以 `lips softly closed` 開場，
  AU6+12（真笑）被鎖在「僅用於淺笑褪去」，懸置拍寫死「不微笑」——
  **四處都不是同一條規則，但合起來的效果是「任意素材都會被導向壓抑」**，
  而且沒有任何一處寫著「本 skill 只做悲傷」。
  **判準：檢查一個 skill 的傾向時，不要只看它寫了什麼規則，要看它的「選項集」與「範例」往哪邊偏。**
  已修：族群補到 15 族（含 4 正向族）、骨架不指定嘴部、AU6+12 改為依族而定、
  懸置「不解決」分極性、題庫 A 區強制候選橫跨極性。
- **能力邊界表會生鏽，用之前先看日期**（2026-09-26 那次錯誤的總結）：
  `performance-lexicon.md` §8 把「對白口型」列在「做不好」，導致整個 skill 繞去做後期配音，
  而 Kling 3.0 其實原生就會。**兩處文件（能力邊界表、模型參數表）都只記了「能不能送」，
  沒記「送了會怎樣」**。遇到「某能力可不可用」的判斷時，去查官方文件與實測報告，
  不要只查自己維護的表；表上每一條都應該能回答「哪個模型版本、什麼時候測的」。
- **暖色調場景會讓膚色偵測抓錯主體（2026-09-26 `seine-bank-scene` 實測，已修）**：
  秋景／駝色大衣／石牆／落葉的 Cb/Cr 與真人膚色幾乎相同
  （大衣 114.5/144.6 vs 她的臉頰 114.4/147.6 —— **分不開**），
  膚色法因此把**右側石牆與落葉框成主體，人整個在框外**，而信心還回報 1.0。
  **純顏色法在這類場景原理上無解**，必須用結構資訊。
  已加入 **臉部偵測（Haar）優先**：`subject_detect.py` 先偵測臉，用「臉框內部色調是否像膚色」
  濾掉紋理誤判，再依人體比例推出頭部與身體框。
  **判準：`source` 欄位。** `face-haar` = 可信（信心 0.9）；
  `skin-blob` / `skin-blob-lowlight` = 需人眼複核（`warm_false_positive_suspected` 會標記）；
  `gradient` = 只是猜的。
- **景別一律看 `shot_basis`**：有臉時用**臉高占畫面百分比**（電影攝影的正確度量），
  沒有臉時才退回膚色區高度。兩者的數字不可互相比較。
  ⚠️ 坐姿／倚靠會讓對應偏移，`face_h_pct` 一律原樣輸出讓你自己校正。
- **每次讀數都會自動產出 `*_subject_check.jpg`**（`--no-check-image` 可關）。
  **開它一眼再往下走**——這是把「人眼確認」從口號變成檔案的作法。
  紅框=主體、綠框=頭、黃框=臉。框錯了就停下來，不要帶著錯的框往下算 21:9。
- **讀解別憑目視硬猜**：先跑 `read_frame.py`。景別、光源方位、景深、背景結構這四項目視幾乎必錯，
  而它們正好決定運鏡與環境選擇。讀數是事實，讀解是解釋，兩者不可混。
- **景別要用未擴張的膚色框量**：`detect_bbox` 的預設擴張（上 1.1／下 2.6／側 0.6）是為**裁切安全**設計的，
  會一路撐到滿幅。拿它量景別，每張圖都會變成「特寫 100%」（2026-09-25 實測踩到）。`read_frame.py` 已分開處理。
- **幅度檔與提示詞尾段禁令必須一致**：選 C 檔卻留著 `restrained and quiet`，模型會「想動又不敢動」變僵硬。
  見 `prompt-templates.md` §1.2。
- **背影／側臉素材禁止寫「她轉過頭來」**：那等於要求模型生成一張它沒看過的臉，換臉風險最高。
  改走姿態、肩線、後頸與呼吸（`visual-analysis.md` §6 C 型）。
- **多人素材必須先確立主角**：不指定，模型會把注意力分散到第二個人身上。
  用景深、光線或構圖把她框出來，並在提示詞明示只有她是清楚的。
- **首幀表情與目標情緒衝突**：不要用負面詞硬壓首幀（模型會兩邊拉扯）。寫成敘事節拍：「faint smile slowly fades into...」。
  若笑意從根本上褪不去，**換一個情緒方向族**（改走追憶系或溫柔系，這兩族允許笑意殘留）比硬改更省成本。
- **結尾有笑時禁止加 `smiling` 負面詞**：`prompt-templates.md` 建議首幀有笑意時追加 `smiling` 負面詞，但若該片的**結尾 beat 就是含笑收尾**，加了會與最後一拍互咬、把笑意壓死。判準：負面詞不能與任何一個節拍的目標表情衝突，衝突時一律讓位於敘事節拍（2026-09-25 night-train-scene 實測）。
- **反向情形：首幀看鏡頭但敘事要目視別處**：若全片沒有任何 beat 需要看鏡頭，直接加 `looking at camera, eye contact with viewer` 負面詞是安全且有效的（2026-09-25 long-drive-scene 實測）。同一條判準的兩面。
- **體檢腳本膚色 WARN 會誤報**：大片淺色衣物（白／米白外套）或低對比場景會把膚色占比拉到閾值以下。最終以「臉部是否完整可見」為準，別被數字攔掉可用的圖。
- **暖色植被會反方向干擾膚色偵測（兩處都中招）**：橙黃秋葉／暖調前景與膚色同色域，read_frame 會誤報「疑似多人」、finish_219 的主體覆蓋率會虛脹到 100% 判偵測失敗退 y=0（2026-09-25 seine-quay-scene 實測兩次）。處置：人眼確認單人後照常走；21:9 用目視候選窗定案裁切 y，不要收下腳本 fallback。
- **雙焦平面**：室內人物 + 窗外主體，模型焦點轉移不穩，需抽卡或改成單一焦點。
- **環繞幅度**：單張參考圖做 360° 全環繞等於全程腦補，換臉風險極高。默認上限 90–120°。
- **小臉／側臉素材 + 轉頭 + 環繞 = 三重叠加高風險**：當參考圖人臉在畫面裡偏小（約占畫面高度 20% 上下）或為 3/4 側臉時，禁止大角度轉頭與全環繞。兩招對沖（2026-09-25 old-city-scene 實測有效）：① 環繞的同時**緩慢收緊成中景**，讓角色在需要表情的那一拍臉部像素變多；② **用前景運動遮罩風險窗**——見下條。
- **前景運動遮罩換臉風險窗（可複用手法）**：在換臉最高發的那一兩拍（通常是轉頭／環繞中段）安排一個焦外行人橫穿鏡頭，短暫遮住角色。既是城市縱深的三層敘事（前景人流／中景主體／遠景車流），也物理遮蔽最危險的幾幀。硬條件：前景人物必須寫成 `anonymous out-of-focus pedestrians ... soft dark silhouettes, faces never recognizable`，並在負面詞堵 `visible face of foreground pedestrian`、`foreground pedestrian lingering in frame`、`crowd filling the frame`、`foreground person looking at camera`，否則模型會把他當第二主體畫出清楚的臉搶畫面。
- **精細手部動作**：Kling 對手部細節弱。「指尖輕撫圍巾」之類的高精度動作容易被畫壞，改用整體姿態與肩線變化。
- **「精細手指禁令」的適用邊界（2026-09-25 rainy-street-scene 修正）**：禁的是**指尖 articulation**
  （撫摸、捏、撥動），不是所有手部入畫——「整掌抓握手機貼到耳邊」這種**粗握持＋腕臂動作**實測可行
  （omni-reference 多鏡下手指解剖學正確）。判準：動作由腕／臂／肘驅動＝可行；由指節逐節驅動＝禁。
- **動作序列（多步敘事）首選 omni-reference 多鏡，不要單鏡硬塞**：用戶要「收傘→看天→回神→掏手機貼耳」
  這類序列時，開 `customize_multi_shots`（最多 6 鏡），**每鏡只做一件事**，每鏡 prompt 自帶身份錨，
  單鏡 prompt ≤500 字元（見 `references/models.md`）。reference 模式**不吃首幀**——參考圖是身份/場景錨，
  動作可以離開源圖構圖；不要拿 image-to-video 的首幀思維誤判「動作不可做」（2026-09-25 被用戶糾正的教訓）。
- **複雜道具動作（收傘）模型會自己簡化**：把「折疊傘面」處理成「把傘收下帶出畫外」——動作連續性成立、
  電影語言可接受，驗收時按「連續性」而非「逐幀折疊」判，不要因此重跑。
- **`--seed` 與抽卡**：固定參考圖重跑即可，不必糾結 seed。
- **omni 的「畫外旁白」會被附體成畫內台詞（2026-09-26 cafe-passingby-scene 實測，連續兩槍復現）**：
  寫 `a soft female voice says off-screen, quietly: "…"`，omni 把 voice 歸給畫面中的女主角——
  口型同步開始動、落點也無視時間戳提早 1–3.7s；改成 `a female narrator's voice-over from outside
  the scene, distinctly not hers` + 句首加 `she never mouths any words` 仍然復現。
  **kling 反而時間戳準**（4.6–6.1s 命中設計 4.8–6.8s）。結論：**omni 原生路徑只適合「畫內對白」，
  畫外旁白要分離生產**——底片提示詞完全移除台詞（寫 `no voice, no dialogue, only quiet ambience`，
  `audio: true` 照送只出環境音，音量極低約 −53dBFS，混音時墊 6dB），旁白後期 edge-tts
  （zh-HK-HiuMaanNeural，`--rate=-6%` 十字句約 1.7s 語音實長）`adelay` 到設計秒數混入，
  落點由混音精確控制、口型風險歸零。
- **kling 對「短 bob 髮型」源圖會持續拉長頭髮（2026-09-26 同案實測，兩槍復現）**：
  正向寫死 `chin-length bob, never grows longer` ＋ 負面 `long hair, hair past shoulders` 都擋不住，
  v1 過肩長髮、v2 齊肩；omni 同源圖僅略長（齊頸→齊肩）且**全片長度恆定不形變**。
  短髮源圖優先 omni；kling 只在需要負面詞堵其他風險且髮型風險可接受時用。
  **驗收時髮長要對照源圖逐幀看**——check_audio 只管聲音，髮型漂移靜默通過所有自動檢查。
- **結果下載會斷線，但生成已成功（2026-09-26 兩案實測）**：
  `i2v.py` 可能在下載最後十幾 KB 時報 `retrieval incomplete`（例：9,017,280/9,033,450 bytes），
  此時**任務已在帳上、影片已生成**，重跑生成=白花一次錢。解法：拿結果裡的 `local_paths[].url`，
  `curl -sL -C - -o <原檔名> <url>` 斷點續傳補完，`ls -la` 對上預期位元數即用。
  之後照常跑 `check_audio.py` → `finish_219.py`，全鏈路不受影響。
- **Kling 3.0 原生就會出對白，不要繞後期**（2026-09-26 更正舊結論）：環境音、音效、配樂與
  **口型同步的語音**都在同一次生成裡渲染完成，`sound: true` 即可，約 90% 幀對齊。
  後期鋪只在需要精確控制時才用（指定曲目／指定配音員／多語版本）。
- **對白不寫進提示詞引號內 = 啞片**：這是原生音訊**最容易踩的坑**。
  台詞必須是提示詞的一部分（`she says quietly, '沒事了。'`），只寫在 manifest 或設計書不會被唸出來。
  畫面一切正常，只是沒有聲音。建議用 `i2v.py --dialogue` 由腳本組句。
  生成後**一定要跑 `check_audio.py` 驗**。
- **有對白時不要堵 `talking`／`lip sync`**：舊版把
  `talking throughout, mouth moving continuously, lip sync, speaking` 一律放進負面詞——
  那在有對白時會**把對白一起壓掉**。這條負面詞只在「無對白」時用。
  同理，基礎負面詞包裡的 `voiceover` 有旁白時要拿掉。
- **5 秒塞不下對白**：中文上限 ≈8 字（含標點），入戲拍還不能說話。
  用戶想在 5s 講一句完整的話時，直接告訴他唸不完，並建議升到 8s 或改成畫外旁白。
- **環境音選項不能掰**：每個選項都要指得出畫面的哪個元素，或讀數 `acoustic_hint` 的哪個欄位。
  指不出來的選項就是編的，用戶一問就穿幫。
- **「密閉／開闊」不能用景深推**：曠場人物一樣可以是淺景深近距離（大光圈拍人）。
  景深只能推**收音距離**，開闊度要用**上方亮面**（天空訊號）與背景均勻度判斷。
  `read_frame.py` 已把兩者拆成獨立的軸（2026-09-26 修正：初版把曠場人像誤判成「密閉」）。

模型層面的坑（2026-09-25 實測，詳見 `references/models.md`）：

- **omni 的 `resolution` 預設 720p**：不顯式傳 `1080p` 就會拿到 720p。這是**靜默降級**，最容易被漏掉。
- **omni 的 `aspect_ratio` 兩個端點規則相反（最容易踩死的一條）**：
  - `omni-image` 單鏡頭**只能 `auto`**。送 `16:9` → `422 aspect_ratio must be auto for image-to-video without custom multi-shot`，整個請求失敗。要 16:9 只能靠**輸入圖先正規化**。
  - `omni-reference` **只能送具體比例**（`16:9`）。送 `auto` → `500 aspect_ratio is not within the range of allowed options`。
  - **推論陷阱**：拿 `21:9` 去探測會回 `500 not within range`，那**只證明欄位被讀取，不證明 `16:9` 會被接受**。本 skill 曾據此寫下「omni 一律送 16:9」，是被 `omni-image` 的 422 打臉後才更正。以後驗證「某合法值能不能用」，必須拿該合法值去撞**語意規則**，不能只拿非法值撞列舉校驗。
- **omni 沒有 `mode` 也沒有 `negative_prompt`**：送了直接 500。負面控制只能靠正向寫法。
- **kling 的 `mode` 只吃 std / pro / 4K**："2K" 會被拒（`mode is not within the range of allowed options`）。
- **`omni-reference` / `omni-image` 都需模型級授權**：key 未開通該模型時直接 401 `not authorized to use this model`，不要誤判成參數錯誤反覆重試。（2026-09-25 兩者均已開通並寫入 config。）
- **omni-reference 參考圖上限 7 張**（實測 8 張回 `image_urls supports at most 7 files`）。人物圖為事實必備，服裝／場景各一張即可，重複同圖沒有意義。
- **欄位名不同**：omni 用 `audio`，kling 用 `sound`。手寫 payload 時最容易搞錯；腳本已分別處理。
- **多鏡頭與單鏡頭互斥**：情感敘事一律關閉多鏡頭，避免模型自動切鏡破壞單一連續鏡頭。
- **21:9 交付不得切掉主體**：`finish_219.py` 會先偵測主體再決定 crop 或 pad；偵測失敗（覆蓋率 ≥0.92）時**一律貼頂 y=0**。
  **不要用中段偏置當 fallback** —— 低光素材上會悄悄削頭（實測案例：頭頂 y≈20，偏置 y=90 削掉 70px）。
  必要時人工看縮圖確認，並可用 `--subject-y0/--subject-y1` 重裁（不需重新生成）。
- **Apple 播放器黑屏坑（2026-09-25 nordic-plaza-scene 實測）**：crop 高度 **822（非模 16）+ High profile** 的重編檔，
  在用戶的 Apple 播放棧（VideoToolbox 路徑）解碼失敗——症狀是「頂部一條內容、其餘全黑」；
  但 cv2/ffmpeg 後端解碼完全正常，**「cv2 抽幀驗證通過」≠「Apple 棧可播」，別把前者當驗收**。
  解法（已固化進 `finish_219.py`）：裁切高 **snap 到模 16**（822→816，即 2.35:1 變形寬銀幕），
  全線編碼加 `-profile:v main -tag:v avc1`（與實測可播的 kie.ai 母版同一 profile）。
  交付前抽檢串流參數應為 `h264 (Main) (avc1)`。
- **素材上的干擾物要先在源頭處理，不要寫進提示詞賭模型忘記**：前景的手、玻璃上的淡字／浮水印，
  先裁掉或局部模糊再上傳。實測發現「生成物上的文字雜點」其實**存在於原始素材**，
  模型只是忠實複製——曾誤判成模型產物並建議重跑，實際重跑也於事無補（2026-09-25 更正）。
- **用戶要求改服裝／道具／背景時，一樣在源頭做，走 Stage 0.5**，不要寫進生視頻提示詞。
  I2V 模型不會幫你脫外套、不會幫你換裙子——它只會照抄首幀。改造完用**膚色占比**驗收有沒有真的生效
  （露膚量變動時最靈敏；實測 0.0010 → 0.0049 才算過關），並在負面詞堵住改動項回魂
  （2026-09-25 `waterfall-sleeveless-scene` 實測：移除白外套改無袖，外套全程未回魂）。
- **低光／低對比素材的主體偵測會失效**：深灰車艙、夜景、暗調室內會讓膚色遮罩膨脹到覆蓋全畫面。`finish_219.py` 現在把「覆蓋率 ≥ 0.92」判為**偵測失敗**（不是主體真的佔滿），退回預設偏置並在報告標記 `detection: uncertain`；放寬門檻的第二段（`skin-blob-lowlight`）反而更容易過度膨脹，別把它的結果當定論。人工介入手段：`--subject-y0/--subject-y1` 指定主體範圍、`--mode pad` 保守保留全幅、`--also-pad` 一次出兩版並看（2026-09-25 car-window-scene 實測）。
- **omni-image 的首幀跟隨度弱，視線類敘事錨禁用（2026-09-26 doorway-tender 實測）**：
  同一素材 omni-image 首槍三個硬傷：①視線 1.6s 起反向（設計釘畫外左、她轉右，敘事錨被毀）；
  ②露齒張嘴開懷笑（提示詞寫死 lips closed 也擋不住，omni 無負面詞）；
  ③瀏海漂成中分露額（髮型錨漂移）。同素材換 kling pro＋負面詞
  （`teeth, open mouth, looking to the right, bangs parted, hair down`）＋正向三鎖一槍修復。
  **判準：視線方向、唇形閉合、髮型只要有一項承擔敘事意義，選 kling（要負面詞）或 omni-reference（身份錨穩），不要 omni-image。**
  對照組：omni-reference 兩案（cinema-confrontation 等）髮型/身份全片恆定——reference 模式與 image 模式穩定性完全不同級。
- **manifest 頂層是陣列，不是 dict（2026-09-27 letter-in-train 實測）**：
  寫成 `{"shot01": {...}}` 會 `AttributeError: 'str' object has no attribute 'get'`（迭代 dict 得到 key 字串）。
  正確格式：`[{"id": "shot01", "image": ..., "prompt": ...}]`。
- **manifest 音訊欄位是 `audio`，不是 `sound`（2026-09-27 waiting-seat-scene 實測）**：
  SKILL.md 正文多處寫「kling 送 `sound: true`」指的是 **API body 層**；
  但 `i2v.py` 的 **manifest 層**讀的是 `shot.get("audio")`，再自行映射成 kling body 的 `sound`。
  在 manifest 裡寫 `"sound": true` 會被**靜默忽略**（fallback false，出啞片）。
  **判準：乾跑 body 裡 `"sound": false` = 中招**，改 manifest 為 `"audio": true` 再發射。
- **「笑意盛開」節拍下 `teeth` 負面詞壓不住自然露齒（2026-09-27 letter-in-train 實測）**：
  懸置拍的目標表情是笑容盛開時，模型在笑意頂點自然露出上齒，負面詞 `teeth` 對此基本無效
  （負面詞能擋的是誇張咧嘴，擋不住「微笑自然帶齒」這種連貫動作的中間態）。
  判準：露齒若屬自然溫柔微笑（非大笑、無變形、情感方向正確），按「電影語言可接受」判準放行，不為此燒錢重跑。
  要嚴格閉口笑時，**正向寫法比負面詞有效**：`her lips stay gently closed even at the fullest of the smile`。
- **kling 原生音訊响度可能低到不可聽（2026-09-26 night-phone-call 實測，2026-09-27 waiting-seat-scene 再現，letter-in-train 第三例）**：
  kling `sound: true` 生成的音軌整體峰值僅 **-51dB**（帶聲片正常量級 -15dB 峰值）——結構上事件都在（check_audio 找得到候選事件），但物理上聽不見。
  **判準：帶聲交付前必讀 check_audio 的 dBFS 欄（整體/底噪/峰值），不能只看「有沒有音訊流」。**
  解法是一行混音增益，不需重跑畫面：`ffmpeg -i in.mp4 -c:v copy -af "volume=35dB" -c:a aac -b:a 192k out.mp4`（增益後峰值 -17.8dB 可聽；增益量按原始峰值反推，目標峰值 ≈ -16dB）。
- **SFX 落點會偏移**：提示詞寫「約 3.5 秒手機鈴響」，實際音型落在 5.0–5.7s（掏出手機的瞬間）——晚 1.5s 但因果仍通（掏出來時正響）。寫時序 SFX 時落點驗收按「因果是否成立」判，不按秒數硬卡；真實音色必須人耳終驗。
- **低光素材的 21:9 pad 不一定是對的（2026-09-26 cinema-confrontation 實測）**：
  `skin-blob-lowlight` 低信心（0.35）把主體頂誤報在 y=168（實際目視 y≈60），腳本因此判「主體超窗」走 pad。
  人眼複核後手動 `crop y=0` 重裁，頭頂完整保留、構圖遠優於模糊補邊。
  **判準：pad 的理由若是低信心偵測給的主體框，先抽幀目視頭頂位置再收；報告同步標 `manual-measured`。**
- **omni-reference 對「靜態對峙」類 A 克制表演極穩（2026-09-26 同案實測）**：
  5s 全片構圖幾乎不動、髮型髮長恆定、身份鎖死，四拍微表演（下巴微抬／極慢眨眼／視線回收）全部命中。
  對峙系／注視類優先 omni-reference；它無負面詞，銀幕假字、空位被佔、他人入畫一律寫肯定句守則防守
  （`no readable text or letters anywhere` / `the seat beside her stays empty` / `She is completely alone in the frame`），實測全部生效。
- **omni 沒有負面詞 → 排除項必須改寫成正向守則**：把「不要帽子、不要手機、畫面裡不要有別人」寫成 `She is completely alone in the car; no phone, no hat, no bag and no other person appear anywhere in frame.` 這種肯定句。負面詞版本仍要留檔，供日後 kling 重跑使用（2026-09-25 car-window-scene 實測）。
- **參考圖本身帶瑕疵時，先修圖再上傳，不要靠提示詞補救**：圖中有第二人的手 = 先把那塊裁掉（`PIL Image.crop`），比在提示詞裡寫「不要出現手」可靠得多（2026-09-25 實測）。
