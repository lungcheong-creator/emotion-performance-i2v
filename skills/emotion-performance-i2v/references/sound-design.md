# 聲音設計與對白

用途：把「要不要加聲音」這一題，從一句 yes/no 升級成**可執行、可驗收**的聲音設計。

> **⚠️ 2026-09-26 重大更正**
> 本檔初版寫「對白一律後期配，不靠模型生成，因為口型同步不可靠」——**那是錯的**。
> Kling 3.0 **原生**就在同一次生成裡渲染環境音、音效、配樂與**口型同步的語音**，
> 對白不需要後期。已於 2026-09-26 實跑驗證（見 §0.2）。
> 錯因與證據見 `models.md` §4，本檔已依正確事實整份改寫。

## 0 · 兩條交付路徑（先選路徑，再談內容）

| 路徑 | 做法 | 什麼時候用 |
|---|---|---|
| **A · 原生（推薦）** | `sound: true`（kling）／`audio: true`（omni），對白寫進提示詞引號內 | 要對白／旁白／環境音／配樂，且要一次交付成品。**這是主路徑** |
| **B · 後期鋪** | 模型不出音，環境音／配樂／配音全部後期 | 需要精確控制（指定曲目、指定配音員、多語版本、要重混）；或抽卡失敗需要保底 |

**兩條路徑不互斥。**最穩的作法：**先跑原生**，若某一段聲音不滿意，
再用後期在原生音軌上做增益／替換——而不是反過來（先無聲再全配）。

### 0.1 原生路徑的三個硬性事實（決定提示詞怎麼寫）

1. **對白必須寫在提示詞裡，而且要用引號包住。**
   `she says quietly, 'I thought hanging up would be enough.'`
   只寫在設計書或備註裡 → 產出**完全沒聲音**的片子。畫面一切正常，只是啞的。
   （`i2v.py` 的 `dialogue` 欄位已自動組進提示詞，避免這個坑。）
2. **原生音訊要另外付費**：約貴 43–50%（pro 18 → 27 credits/秒）。報價時要講。
3. **環境音是自動的**，不用寫也會有；要壓低就加 `quiet` / `silent` / `hushed`。

### 0.2 實跑驗證（2026-09-26，`sound-verify-5s`）

|---|---|
| 任務 | `kling-3.0/video`，`sound: true`，pro，5s，對白「沒事了。」 |
| taskId | `f6b8b293696aa395f6a83c4bdb62d8e7` |
| 耗時 | 2m56s |
| 輸出 | 1920×1080 / 24fps / 5.04s |
| **音訊流** | ✅ **aac (LC) 44100Hz stereo 128kb/s**（同期無音訊對照組：完全沒有音訊流） |
| 語音內容 | 環境底噪穩定 −35dB，**t=3.0–3.6s 出現 −22.9dB 能量峰**，300–3400Hz 人聲共振峰帶佔 51.3% → 確認為語音事件 |
| **對白落點** | 落在 **3.0–3.6s**，即 5s 結構的**轉折帶**（2.8–3.8s）——模型照敘事節奏放，沒有從頭就講話 |

**兩個可複用的結論**：

1. **模型會自己把對白放在後段**，不會糊在開頭。這與「對白不上入戲拍」的規則一致，
   等於規則得到了實證支持。（但仍要寫清楚，不要靠模型猜。）
2. **實測語速比規劃值快**：4 個中文字只用了約 0.6s（≈5.7 字/秒），
   明顯快於 §6 規劃用的 3.5 字/秒。**這個保守差距是刻意的**——
   寧可讓台詞短一點、講慢一點像在演戲，也不要塞滿變成念稿。

**結論：兩個模型（`kling-3.0/video` 與 `kling-3.0-omni/image-to-video`）都能原生產出
含口型同步的對白，不需後期。** omni 的路徑也補實了。

**粵語**：kie.ai 的功能對照表把 **「Dialects and Accent Simulation（方言與口音模擬）」列為
Kling 3.0 相對 2.6 的新增能力**（2.6 為「不支援」）。本次實跑確認模型照粵語台詞產出了
對應音節數的語音。**但「聽起來像不像粵語」需要人耳判斷**——
自動化量測只能證明「有語音、音節數對、口型對得上」，證不明「口音純不純」。

**仍然未驗證**：omni 的**音色參考**（`element_input_audio_urls` 等同物）。
該槽位只在 `kling-3.0/video` 的文件中出現；omni 只有 `elements`。
`i2v.py` 遇到 omni ＋ `--voice-ref` 會明確提示「kling 專屬」。

### 0.4 第三支驗證：**omni-reference ＋ 粵語**（2026-09-26，真實生產案例）

`seine-bank-scene`：`kling-3.0-omni/reference-to-video` ＋ `audio: true` ＋ 16:9 ＋ 1080p ＋ 8s，
對白「**又一年秋天，你幾時返嚟？**」（12 字，粵語）。

| 項目 | 結果 |
|---|---|
| taskId | `f739629a23868e2c1150adb9e02b134a` |
| **耗時** | **13m49s**（同條件的 omni-image 5s 只要 1m52s——reference 模式明顯慢得多） |
| 輸出 | 1920×1080 / 24fps / 8.04s |
| **音訊流** | ✅ aac (LC) 44100Hz stereo 128kb/s |
| 語音判定 | `HAS_SPEECH`，人聲帶佔比 46% |
| **動態範圍** | **50.4 dB**（前幾支只有 15–18 dB → 這一支的音軌內容豐富得多） |
| 語音事件 | **4.4–5.6s**（峰 −9.0dB）與 **6.2–7.2s**（峰 −10.4dB）——正是那句話的兩個分句 |
| **口型同步** | ✅ 逐幀目視確認：4.4–6.4s 嘴部持續開合，7.6／7.9s 閉合放鬆 |

**結論：`omni-reference` 同樣支援原生對白與口型同步。三個模型至此全部補實。**

**同時暴露的取捨（下一個要選這個端點的人必須知道）**：

1. **不吃首幀 → 構圖會重構。** 同一支片內，臉中心 x 由 1086 漂到 1138 再回到 1084，
   臉高由 15.1% 長到 18.1%——推近被重新詮釋，構圖不是「照著首幀長大」，而是**重新生成一個類似的鏡頭**。
   若要嚴格鎖住姿勢與構圖，用 `kling` 或 `omni-image`。
2. **沒有負面提示詞** → 背景元素（本案例的貨船）會有些被重新解釋。只能靠正向寫法明確指名。
3. **慢**：13m49s vs 1m52s（omni-image）。單圖任務用它是浪費。

## 1 · 三層聲音結構（設計維度）

| 層 | 內容 | 原生路徑能不能給 | 後期路徑 |
|---|---|---|---|
| **L1 環境音** | 底噪、空間感、事件音 | ✅ 依場景描述**自動生成**；寫進提示詞會更明顯 | ✅ 自由 |
| **L2 配樂** | drone、單音樂器、節奏 | ⚠️ 場景暗示音樂時會生成，**不能指定曲目/BPM/調性** | ✅ 自由 |
| **L3 人聲** | 畫外旁白 / 畫內對白 | ✅ **含口型同步**（≈90% 幀對齊） | ✅ 自由（配音員／TTS） |

**默認建議：L1 原生 ＋ L2 讓模型自己給或極簡後期 ＋ L3 視需要。**

## 2 · L1 環境音：選項必須來自畫面

**硬規則：每一個環境音選項都要指得出畫面的哪個元素。**
禁止給「溫暖的城市夜晚」這種和畫面無關的選項——那是沒看圖的人才會給的。

選項的兩個來源：

1. `read_frame.py` 的 `acoustic_hint`（音場底色）
2. 讀解的可動環境元素清單（`visual-analysis.md` §3，具體音源）

### 2.1 畫面證據 → 音場底色

| 讀數證據 | 推得的音場 |
|---|---|
| `enclosure` = 開闊（上方有亮面：天空／大片窗光） | 沒有回彈，聲音散掉；風與遠處底噪為主 |
| `enclosure` = 密閉（上方暗且被遮：天花板／車頂／樹冠） | 低頻堆積、有回彈；呼吸與衣料摩擦在收音範圍內 |
| `density` = 安靜（背景高度均勻） | 單一持續底噪，任何事件音都會很突出 |
| `density` = 規律 | 可預期的重複聲源（滴漏、腳步、規律車流） |
| `density` = 熱鬧（結構密集） | 不規則多方聲源；個別聲音不可辨 |
| `distance` = 近距離（淺景深 + 主體大） | **把呼吸寫進音軌**——這是近距離最強的一招 |
| 低光 | 低頻為主；遠處車聲／電器嗡聲 |
| 明亮戶外 | 高頻為主；開闊感強 |

### 2.2 可動元素 → 具體音源

| 畫面元素 | 可用的音源 |
|---|---|
| 髮絲／衣角偏移 | 風（起風、風聲忽大忽小） |
| 雨的斜度 | 雨打在不同材質上的層次（玻璃／傘／地面） |
| 水面／玻璃／金屬反光 | 反射與空洞感；遠處水聲 |
| 天空／霧／素牆 | 極低量的空氣流動聲（幾乎聽不見的那種） |
| 人群／街景 | 無個別可辨的人聲底噪、車流、腳步 |
| 塵埃／飛絮 | 停滯感；退到幾乎無聲 |
| 車流／燈光 | 週期性的通過聲，由遠及近再遠去 |
| 室內低光 | 電器嗡聲、遠處車聲、建築自身的低鳴 |

**提問時給 ≥3 個選項，每個都要標出它的畫面依據。** 例：

> E1 ★推薦：**城市夜間底噪 + 車流**——依據：讀數 `密閉`（車艙）＋ `低光`＋背景結構密集
> E2：**只留下呼吸與布料摩擦**——依據：`近距離`（淺景深、主體佔畫面大），把環境壓到最低
> E3：**遠處雨聲，隔著玻璃**——依據：車窗玻璃反光；雨在玻璃外，聲音是隔一層的
> E4：**我自己指定**

**原生路徑的寫法**：把選中的音源寫進提示詞（`the rain hammers the tin roof` 比只寫「下雨的場景」顯著得多）；
要壓低就加 `quiet` / `silent` / `hushed`。

## 3 · L2 配樂

| 選項 | 內容 | 說明 |
|---|---|---|
| M1 | **不指定，讓模型自己給** | 場景暗示音樂時模型會生成。最快，但不可控 |
| M2 ★推薦 | **極簡 drone（後期）** | 大提琴／合成器低頻長音，不解決。承擔「時間感」，且完全不搶表演 |
| M3 | 稀疏單音（後期） | 鋼琴／吉他單音，60–68 BPM 小調。單音之間留大量空白 |
| M4 | 用戶指定（後期） | 曲名／風格／情緒；若給了參考曲，記進溯源表 |

**配樂的兩條鐵律：**

1. **結尾不解決。**不要在懸置拍上收和弦——那等於替觀眾收情緒。
2. **不與對白搶。**原生路徑的配樂音量不可控，所以**有對白時建議 L2 走後期**——
   這樣才能把配樂壓到 −18dB 以下，並在對白前後各讓出 0.3–0.5s。

**原生配樂的限制（必須如實告知）**：不能指定具體曲目、BPM 或調性；
生成的是原創音樂（無版權問題），但品質適合當背景，不是製作級配樂。

## 4 · L3 人聲：四個選項

| 選項 | 內容 | 原生路徑可行性 | 適用 |
|---|---|---|---|
| **V1** | **無聲** | `sound` 仍可開，只有環境音 | 5s 低資訊量時；或走純環境敘事 |
| **V2** | **畫外旁白** | ✅ 可行（對白寫進提示詞，但畫面寫明她沒開口） | 8s 以上；追憶系／疲憊系 |
| **V3 ★推薦** | **畫內對白（含口型同步）** | ✅ **Kling 3.0 的強項**，≈90% 幀對齊 | 8s 以上；搭配 §5 的降險手段 |
| **V4** | **用戶自定義台詞** | ✅ 照 §6 檢查長度 | 任何 |

**V2 與 V3 的差別要講清楚給用戶聽：**
V2 是「有人在說話，但不是她」——敘事上常更強（觀眾聽到的是她的內心）。
V3 是「她真的開口」——**Kling 3.0 會做出對得上的口型**，但首字與尾字最容易飄。

**若用戶想指定音色**（例如多鏡頭要同一個聲音）→ 用 `kling_elements` 的音訊參考（5–30 秒樣本），
**只有 `kling-3.0/video` 支援**（`i2v.py --voice-ref`）。omni 的音訊參考未驗證，不要承諾。

## 5 · 降低口型風險（V3 專用）

原生口型同步已可用，但**不是 100%**。來源標註：約 90% 幀對齊，
**首字與尾字最容易飄**，說話者越多越差。

**五個降險手段，按有效性排序：**

1. **一句到底，不要在同一個鏡頭換說話者。** 單人最佳；兩人以上精度明顯下降。
2. **台詞短。** 這是最好用的手段——短句飄的絕對量小（見 §6）。
3. **對白落在停頓拍或轉折拍。** 那兩拍頭部動作本來就小，口型誤差不易被看見。
   **實測（§0.2）：模型自己就把對白放在轉折帶。**
4. **必要時用「看不見嘴的角度」**（側臉／低頭／手遮／背對）——
   這仍然是**最保險的手段**，用於台詞較長或抽卡失敗時。
5. **抽卡重跑。** 口型失準是隨機的，重跑同一提示詞常常就對了。
   **不要為了口型改提示詞內容**（那會動到表演設計），先重跑再說。

**禁止事項：**
- 禁止要求模型做「精確口型」（它自己會對；寫了只是浪費提示詞額度）
- 禁止長句（見 §6）
- 禁止在每個拍都開口（那會變成「嘴一直在動」）

## 6 · 對白長度硬限（依時長）

**規劃用語速：中文 3.5 字／秒、英文 2.5 詞／秒**（含標點，標點算暫停）。
對白前後各留 0.3–0.5s 氣口，且**入戲拍不說話**，所以可用秒數小於片長。

| 時長 | 可用於說話 | 中文上限 | 英文上限 |
|---|---|---|---|
| **5s** | ≤ 2.5s | **≈8 字** | **≈6 詞** |
| **8s** | ≤ 3.5s | **≈12 字** | **≈8 詞** |
| **10s** | ≤ 4.5s | **≈15 字** | **≈11 詞** |
| **15s** | ≤ 6.0s | **≈21 字** | **≈15 詞** |

**超過上限 → 硬擋（`DIALOGUE_TOO_LONG`），要求刪短**，不是警告。
理由：來源明確指出越長越容易失準，且**首字與尾字最容易飄**——
過長的台詞不是「唸快一點就好」，是會**看得出來壞掉**。
`i2v.py --allow-long-dialogue` 可覆寫（接受失準）。

**這個上限刻意保守。**實測（§0.2）顯示模型實際語速約 5.7 字／秒，
比規劃值快得多；但那樣的語速聽起來像念稿，不像演戲。
**寧可短、寧可慢。**

寫對白時先把字數數出來，再寫內容。**字數是硬約束，內容在約束裡挑。**

## 7 · 對白與節拍對齊

對白不是鋪在整支片上，是**掛在某一拍**。

| 落點 | 效果 | 適合 |
|---|---|---|
| 入戲拍 | **禁止**。那時她還沒進入狀態，開口會讓整支片失去鋪墊 | — |
| **浮起拍** | 洩漏——把心裡話漏出來一點 | 畫外旁白（V2） |
| **停頓拍** | 忍到不能忍才吐出來 | 內斂；需縮短停頓拍 |
| **轉折拍** | **開口即換招** | **最強，推薦**。V2／V3 都適用。**實測模型也落在這裡** |
| **回收拍** | 事後的補充、自嘲、收回 | 對白是「講給自己聽」 |
| **懸置拍** | 自言自語，無人回應 | 最孤獨；用於結尾一句 |

**四條規則：**

1. **對白不上入戲拍。**
2. **若全片只有一句對白，那一句就是全片的落點**——放在轉折拍或懸置拍，不要浪費在開頭。
3. **對白要扣著前情**（`visual-analysis.md` §4.3）與情緒方向族（`acting-logic.md` §4）的內在動作。
   壓抑系的對白是「沒說完的話」；決心系的對白是「說給自己聽的確認」；
   警覺系的對白是「短促的疑問」。**對白不能是通用的感嘆。**
4. **時間戳要寫進提示詞**（`around the fourth second she says ...`），
   不要讓模型自己決定何時開口。模型放的位置通常合理，但**可控優於合理**。

---

## 8 · 反幻覺與一致性

- 對白內容可以是推定的（作為候選），但**必須標明是推定**，並讓用戶可改。
- 對白若與前情衝突 → **改前情或改對白，不可兩者並存**。
- 用戶自定義對白若有錯字、語病或不符角色語域 → 先回讀確認，不要擅自改寫後假裝是用戶寫的。
- 用戶自己寫的對白要**逐字**進溯源表。
- **負面詞不要與對白打架**：`performance-lexicon.md` 舊版把 `voiceover` 放進基礎負面詞包，
  那會壓制旁白。開原生音訊時務必把 `voiceover` 拿掉（`prompt-templates.md` §2）。
  同理，收斂約定裡的 `no narration` 也要依「有沒有 L3」變化。

---

## 9 · 提示詞層面的配合

### 9.1 原生路徑：對白要寫進提示詞

```
... she says quietly, '沒事了。' ...
```

**時間戳 ＋ 語氣 ＋ 引號**，三件都要。用 `i2v.py --dialogue`（或 manifest 的 `dialogue` 欄位）
會自動組好，避免手寫漏掉引號。

### 9.2 嘴部狀態：依「有沒有對白」變化

| 情況 | 正向詞 | 負面詞 |
|---|---|---|
| 完全無對白（V1） | `her lips stay softly closed throughout` | `talking, mouth moving continuously, lip sync, speaking` |
| 對白在某一拍（V3） | 該拍寫 `around the fourth second she says ...`；**其他拍寫** `every other part of her body still` | **不要**堵 `talking`／`lip sync`（會把對白一起壓掉） |
| 畫外旁白（V2） | `she does not speak at any point; her lips stay closed` | `visible lip sync, mouth forming words` **＋ 移除基礎包的 `voiceover`** |

**舊版的錯誤做法**：不分情況一律堵 `talking throughout, lip sync`。
那在有對白時會**直接把對白壓掉**——這是舊結論留下的第二個地雷。

## 11 · 怎麼用這份檔案

1. 讀解完成 → 取 `acoustic_hint` 與可動元素清單
2. 先問 §0 的**路徑**（原生／後期）——**默認推薦原生**
3. 題庫 G 區問 L1（≥3 個帶畫面依據的選項）→ 問 L2 → 問 L3
4. 若選 V3／V4（要對白）→ 追問內容，用 §6 的字數上限**當場硬擋過長的**；
   用 §7 決定落點並寫進提示詞的時間戳
5. 用 §5 做口型降險評估；用 §9.2 決定嘴部詞與負面詞（**注意移除 `voiceover`**）
6. 用 §10 產出聲音設計表，進 Gate 1 與交付物
7. **生成後驗收音軌**（`scripts/check_audio.py`）：確認有音訊流、有語音事件、落點符合設計
8. **口型要目視確認**——自動化驗不了，見下

### 11.1 口型為什麼不能用程式驗，以及替代做法

**自動化像素比對實測失敗**（2026-09-26）：全畫面幀差與臉部區幀差的「語音期間 vs 語音外」
比值只有 **0.89×–1.06×**，訊號完全被運鏡、顆粒、身體位移蓋掉。
**不要為了交差報這個假數字。**

**可行的做法是產一張「嘴部放大連續格」交人眼判**（實測有效）：

```bash
# 1) 先用 check_audio.py 找出語音窗（例如 2.10–3.80s）
# 2) 以語音窗為中心取 8–10 個時間點抓幀
ffmpeg -v error -y -ss <t> -i out.mp4 -vframes 1 -q:v 2 f_<i>.jpg
# 3) 裁到嘴部（臉部框上緣往下 60%–90% 那一段），提亮 2×（低光素材必須提亮）
# 4) 排成一張圖，語音窗內的格子加色框
```

**判讀標準**：語音窗內應出現**開口／閉合／圓唇前突**的交替，
且窗後唇部回到閉合靜止。**若語音窗內外的嘴形沒有差別，就是口型沒對上**（kling 無負面詞可救，
直接重跑）。圓唇音（「唔」「住」「烏」）是最容易辨識的判準點。

參考產物：`sound-verify-5s/mouth-strip.jpg`（kling）、`sound-verify-omni-canto/mouth-strip.jpg`（omni）。
